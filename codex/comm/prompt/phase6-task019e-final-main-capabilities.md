## Architecture rules (EA decisions are authoritative)
1. **Direct mapping:** Module ICD source corpus → Main Business Capability candidates → direct ICD links with exact source page/document/service IDs and evidence. Do not derive, store, use or gate on Business Functions or Sub Capabilities. All eligible ICDs must be enumerated and either linked or explicitly unresolved; no silent disappearance, no fabricated link.
2. **Distinct Contracts lifecycles:** Preserve separate meaningful Main candidates for Employment Contract Lifecycle Management, Employment Contract Termination Management, External Contract Lifecycle Management and Training Contract Lifecycle Management where supported. Do not merge these purely because each is a lifecycle. External parties *creating employment contracts* still perform contract-lifecycle activity: map according to contract purpose, NOT automatically to Integration because the actor is external.
3. **EA semantic resolutions:** Contracts Admission Journey belongs under the appropriate **Contract Compliance Management** capability (name clearly; use real evidence and do not create an unsupported catchall); external-entity-created contracts belong to the appropriate contract lifecycle. Existing R3 ambiguity for missing contract type is EA-resolved by Compliance membership. If document evidence conflicts with the EA-directed placement, flag an explicit contradiction rather than silently overriding source.
4. **Legacy/unused:** If a document/service is *explicitly marked* `OLD`, `Old Design`, `NOT USED`, `IGNORE`, `IGNORED`, or `to be deleted` in its title or authoritative metadata, **IGNORE it for the active Main Capability inventory and links**. Record its **exact source identity**, marker and reason in `excluded_sources.csv` instead; do not delete it, do not infer production-retired/runtime-unused status from the marker, and do not sweep unrelated content containing incidental words “old” or “ignore”. Counts of active eligible, excluded, unreadable, unresolved must be separate. Do not silently drop it.
5. **Integration Capability:** When ICD or ISD evidence names an actual external integration entity (e.g. GOSI, NIC, HRSD), create/map a meaningful Main capability such as `<Entity> Integration Management` or `Government Integration Management` within the **same Module**. Preserve the named entity/ies as explicit evidence/attribute. Apply to evidence of real integration/sync/verification activity, not an entity merely mentioned in background or an external actor performing a business process. Existing Contracts external-authority synchronization can be normalized to integration naming on this basis. Avoid one unnecessary capability per incidental mention.
6. **Naming:** All Main names must be clear single business-ability noun phrases, e.g. `Establishment Records Management`, `Contract Template Management`, `GOSI Integration Management`. No slash-delimited keyword concatenations and no bare generic one-word labels. Do not hide distinct functions by relabeling blindly. Logo/Branding and Stakeholder Notification are valid Main candidates where evidence supports them; do not suppress due to small ICD counts. Preserve Module ownership; no cross-Module merge in this task.

## Exact order — repeat for each Module
**Step A — ICD corpus (FIRST):** Select one Module from the recovery effective catalog. Enumerate all its Services, ICD occurrences, unique ICD pages, ISD occurrences and explicit excluded-source markers. Read **all active eligible ICDs** with existing local parser. Produce a coherent **Main Capability inventory and direct Main→ICD links**, backed by actual description/flow/business semantics (not title-only keywords); allow multiple justified Main links. Count every ICD as mapped / excluded / unresolved; preserve identity, evidence block/offset and source version. DO NOT inspect ISD body before ICD taxonomy is complete for the Module.

**Step B — ISDs not linked to ICD (LAST step of that Module, after ALL ICD→Main processing):** Determine precisely which active ISD documents/services have **no evidenced relationship to an ICD** using existing source Service/Document associations and parent-child provenance; do not invent ICD–ISD pairings based on similar names. For these unpaired ISDs **one by one**, read the local ISD content and extract ONLY the minimum classification signals: (1) source Service name; (2) Introduction/Summary/Purpose; (3) meaningful request/response Schema names, structures and business objects (including operation names when available as clues). Then **map ISD directly to an existing Main Capability** using evidence and semantic fit; **create a new Main Capability only if clearly necessary and evidence-supported**, e.g. a real named external Integration Capability. Maintain `Main → ISD` source links and exact evidence, never pretend this creates an ICD. No full endpoint/operation inventory, canonical matching, business function extraction, API schemas export, or new data-model pipeline. ISDs already related to an ICD are **not** re-parsed for classification; preserve their original source relationships for future API mapping.
 
**Step C — Module completion gate:** Reconcile **all** module ICD/ISD references including eligible, excluded, mapped and precise unresolved; report actual Main boundaries, all ISD-only cases resolved/unresolved, and any duplicates/shared pages without inflated counts. Do not call Module semantically complete merely because every readable document has some generic label. Write compact checkpoint then advance to next Module. If a true source integrity blocker occurs, surface it immediately with identity and impact, continue independent Modules without repairing upstream content, and report it plainly.
